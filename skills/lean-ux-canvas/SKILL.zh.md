## 目的

指导产品经理创建 **Jeff Gothelf的精益UX画布（v2）**——一个单页引导工具，将工作围绕**要解决的业务问题**而非**要实施的解决方案**进行框定。使用此技能来对齐跨职能团队的核心假设、制作可测试假设，并确保通过暴露理解中的差距（问题、用户、价值以及为什么解决方案应该有效）每Sprint都能发生学习。

这不是路线图或功能列表——它是**"保险单"**，将假设转化为实验，然后再进行全面开发。画布将对话从**产出**转向**成果**，并确保团队构建正确的事物，而不仅仅是正确地构建事物。

## 关键概念

### 什么是精益UX画布？

**精益UX画布（v2）**是一个结构化的单页模板，旨在帮助团队将工作围绕业务问题而非解决方案进行框定。它对齐跨职能团队对以下内容的理解：
- 存在什么问题（以及为什么现在重要）
- 什么可衡量的成果表明成功
- 我们在为谁解决问题
- 我们在做什么假设
- 我们首先需要学习什么
- 什么实验将测试这些假设

**来源：** 由《*Lean UX*》（O'Reilly，2013）作者Jeff Gothelf创建。v2版本发布以提高业务成果与用户成果的清晰度。

**关键洞察：** 画布像**保险单**一样运作——在构建前暴露理解中的差距，确保您不会在错误的事情上浪费Sprint。

---

### 画布结构（8个格子）

**布局（3列×3行）：**

```
┌─────────────────────┬──────────────┬───────────────────────┐
│ 1. 商业问题         │              │ 2. 商业成果            │
│                     │              │                       │
├─────────────────────┤ 5. 解决方案  ├───────────────────────┤
│ 3. 用户             │  (高格子     │ 4. 用户成果            │
│                     │   跨越       │    和收益              │
│                     │   行1-2)     │                       │
├─────────────────────┤──────────────┼───────────────────────┤
│ 6. 假设             │──────────────│ 8. 最小工作量 /        │
│                     │ 7. 首先学习  │    实验                │
│                     │              │                       │
└─────────────────────┴──────────────┴───────────────────────┘
```

**8个格子（按此顺序填写）：**

1. **商业问题** — 世界发生了什么变化创造了一个值得解决的问题？
2. **商业成果** — 什么可衡量的行为变化表明成功？
3. **用户** — 您应该首先关注哪些用户画像？
4. **用户成果和收益** — 用户为什么会寻求这个？他们获得什么收益？
5. **解决方案** — 什么功能/举措可能解决问题并满足用户需求？
6. **假设** — 结合格子2-5的可测试假设（如果/那么格式）
7. **首先学习什么最重要？** — 现在风险最大的单一假设
8. **学习下一个最重要的是什么最少工作量？** — 验证/证伪该假设的最小实验

---

### 为什么这有效

**问题优先，而非解决方案优先：**
从"世界发生了什么变化？"开始，而非"我们应该构建X"。这防止了解决方案驱动的思维。

**假设驱动：**
在构建前明确假设。每个职能部门都会暴露其风险（技术可行性、用户价值、商业生存能力）。

**实验重点：**
在投入资源前测试假设。小实验优于大赌注。

**跨职能对齐：**
共享画布创造共同语言。每个人都看到相同的理解差距。

---

### 关键区别（避免混淆）

**格子2（商业成果）vs. 格子4（用户成果）：**
- **格子2：** 可衡量的**行为变化**（留存率、网站停留时间、平均订单价值）
- **格子4：** **目标、收益、情感、同理心**（省钱、升职、花时间陪伴家人）

格子2是指标。格子4是人。

**解决方案（格子5）是假设，而非承诺：**
列出候选解决方案（功能、政策，甚至商业模式转变）。您不是承诺构建所有这些——您是在探索解决方案空间。

**假设（格子6）是可测试的：**
使用模板："我们相信，如果[用户]通过[解决方案]获得[收益]，[商业成果]将实现。"每个假设聚焦于**一个**解决方案。

---

### 反模式（这不是什么）

- **不是功能列表：** 解决方案是要测试的想法，而非待办列表
- **不是项目计划：** 画布框定学习，而非交付时间线
- **不是战略的替代品：** 画布执行战略；不创造战略
- **不是一次性练习：** 随着学习重新访问；更新假设

---

### 何时使用

✅ **在以下情况下使用：**
- 开始新的产品举措或功能
- 重新框定现有项目（怀疑您构建了错误的事物）
- 对齐跨职能团队的假设和实验
- 规划发现Sprint或MVP
- 利益相关者是解决方案驱动的（"我们需要构建X"），您需要暴露假设

❌ **在以下情况下不要使用：**
- 问题和解决方案已经验证（转向执行）
- 战术性错误修复或技术债务（不需要学习）
- 利益相关者无论如何证据都已承诺解决方案（首先解决对齐）

### 问题1：商业问题（格子1）

**Agent提问：**

**企业有什么问题您正试图解决？**

描述：
- **当前状态：** 企业今天如何提供价值？
- **发生了什么变化：** 市场转变、竞争威胁、客户行为变化、新交付渠道
- **为什么重要：** 为什么当前情况不符合预期？

**好的示例：**
- "我们的结账转化率在移动流量超过桌面后下降了15%。我们的结账流程不是为移动端设计的，竞争对手有一键结账。"

**糟糕的示例（太模糊）：**
- "我们需要增加收入"（没有说明发生了什么变化）
- "用户想要更多功能"（没有说明业务问题）

3. **我不确定业务问题是什么** — [Agent建议先从 `skills/problem-statement/SKILL.md` 或 `skills/problem-framing-canvas/SKILL.md` 开始]

**用户响应：** [选择或描述]

### 问题2：商业成果（格子2）

**Agent提问：**

**您如何知道您解决了业务问题？您将衡量什么？**

专注于**可衡量的行为变化**（欢迎领先指标）。问自己："如果解决方案有效，人们会有什么不同的行为？"

**商业成果示例：**
- 将移动端结账转化率从45%提高到60%
- 将企业入职时间从3周减少到3天
- 将平均订单价值从$50提高到$75
- 将客户支持工单减少30%
- 将免费到付费转化率从5%提高到10%

**重要：** 这是**格子2（行为变化）**，不是格子4（用户收益/同理心）。指标放这里。情感放格子4。

3. **我只有滞后指标（收入、利润）** — [Agent帮助识别预测这些结果的领先指标]

**用户响应：** [选择或描述]

**Agent验证：** 这些可衡量吗？可观察吗？它们表明行为变化吗（不仅仅是"增加收入"）？

### 问题3：用户（格子3）

**Agent提问：**

**您应该首先关注哪些类型的用户（即用户画像）和客户？**

考虑：
- 谁**购买**它？
- 谁**使用**它？
- 谁**配置**它？
- 谁**管理**它？

**为什么这很重要：** 团队倾向于在这里走捷径（"每个人"）。画布需要用户的一个**共同愿景**——它并不总是"客户"。

**示例：**
- "专业服务（顾问、会计师、律师）的SMB所有者（1-10名员工）"
- "为企业500+员工配置SSO的企业IT管理员"
- "每周订购外卖3次以上的移动优先千禧一代（25-35岁）"

**Agent提供3个选项：**

1. **我已经有用户画像了** — [参考 `skills/proto-persona/SKILL.md` 或粘贴用户画像]
2. **帮助我识别目标用户** — [Agent提问：谁最常经历业务问题？谁最有可能采用？谁最容易接触？]
3. **我需要先创建用户画像** — [Agent建议使用 `skills/proto-persona/SKILL.md` 组件技能]

**用户响应：** [选择或描述]

**Agent验证：** 这是否足够具体到可以想象一个真实的人？还是太宽泛（"所有用户"）？

### 问题4：用户成果和收益（格子4）

**Agent提问：**

**为什么您的用户会寻找您的产品或服务？他们会获得什么收益？我们可以观察到什么行为变化表明他们实现了目标？**

专注于**目标、收益、情感、同理心**——不是指标（那些放格子2）。

**用户成果和收益示例：**
- 每周节省10小时手动数据录入（花更多时间陪伴家人）
- 通过更快交付项目获得晋升
- 避免在朋友面前结账失败的尴尬
- 对配置企业软件而不致电支持感到自信

**为什么这很重要：** 这是**同理心格子**。它是关于人类动机，而不仅仅是行为变化。

1. **我知道用户想要实现什么** — [描述用户收益]

3. **我需要先研究这个** — [Agent建议 `skills/jobs-to-be-done/SKILL.md` 或 `skills/discovery-interview-prep/SKILL.md`]

**用户响应：** [选择或描述]

**Agent验证：** 这是否解释了用户**为什么**关心（而不仅仅是他们会做什么）？

### 问题5：解决方案（格子5）

**Agent提问：**

**我们可以做什么来解决我们的业务问题，同时满足客户的需求？**

### 问题7：我们首先需要学习的最重要的事情是什么？（格子7）

**Agent提问：**

对于格子6中的每个假设，识别其**风险最大的假设**。然后确定**现在风险最大的一个**。

**风险类型：**
- **价值风险：** 用户真的会使用这个吗？他们关心吗？
- **可用性风险：** 用户能弄清楚如何使用它吗？
- **可行性风险：** 我们能从技术上构建这个吗？
- **生存能力风险：** 这会实现业务成果吗？

**提示：** 早期，专注于**价值**风险而非可行性（大多数时候）。不要构建用户不想要的东西，即使它在技术上是可行的。

**Agent提供：**

根据您的假设，以下是风险最大的假设：

1. **[假设1风险]** — 例如，"用户会信任一键结账而看不到逐项费用"
2. **[假设2风险]** — 例如，"自助入职会将设置时间减少到<3天"
3. **[假设3风险]** — 例如，"AI推荐会将平均订单价值提高50%"

**哪一个现在是风险最大的？**

**选项：**
1. **风险1** — [选择并解释为什么]
2. **风险2** — [选择并解释为什么]
3. **风险3** — [选择并解释为什么]
4. **我不确定哪个风险最大** — [Agent帮助排序：如果哪个假设错了会扼杀这个举措？]

**用户响应：** [选择]

**Agent记录：** 这是我们将首先测试的假设。

### 问题8：我们需要做最少的工作来学习下一个最重要的事情是什么？（格子8）

**Agent提问：**

设计一个实验来**尽快**验证或证伪风险最大的假设（来自格子7）。

**实验类型示例：**
- **客户访谈** — 5-10次访谈来测试价值假设
- **落地页** — 假门测试来衡量兴趣
- **礼宾/手动原型** — 自动化前的高接触、人工版本
- **绿野仙踪** — 假装功能存在（幕后是人类）
- **烟雾测试** — 宣布功能，衡量注册量

**提醒：** 实验设计是一门艺术。画布推动您去做——预期会单独迭代实验设计。

**Agent提供：**

根据您的风险最大假设，以下是实验选项：

1. **客户访谈** — 与10个用户交谈，询问他们是否会使用[解决方案]，观察他们当前的变通方案
2. **落地页测试** — 创建一个描述[解决方案]的落地页，衡量注册率
3. **礼宾测试** — 手动为5个用户提供[收益]，观察他们是否实现[成果]
4. **绿野仙踪原型** — 用幕后的人类伪造[解决方案]，看看用户是否完成工作流
5. **设计自定义实验** — [描述您的实验]

## 常见陷阱

### 1. **从解决方案开始，而非问题**
**失败模式：** 格子1说"我们需要构建X"而不是描述发生了什么变化。

**后果：** 您构建了某人已经决定的解决方案，而没有验证问题存在。

**修复：** 问："世界发生了什么变化？为什么现在这是个问题（vs. 6个月前）？"

---

### 2. **模糊的商业成果**
**失败模式：** 格子2说"增加收入"或"让用户快乐"。

**后果：** 无法衡量成功；无法判断实验是否有效。

**修复：** 定义可衡量的行为变化。"将平均订单价值从$50提高到$75"或"将支持工单减少30%"。

---

### 3. **太宽泛的用户细分**
**失败模式：** 格子3说"所有用户"或"每个人"。

**后果：** 无法设计针对性实验；在不会采用的用户画像上浪费时间。

**修复：** 选择一个用户画像开始。您可以稍后扩展。

---

### 4. **混淆格子2和格子4**
**失败模式：** 将情感放在格子2，将指标放在格子4（或反之）。

**后果：** 假设不一致；成功标准不清晰。

**修复：** **格子2 = 行为变化（指标）。** **格子4 = 目标、收益、情感（同理心）。**

---

### 5. **格子5中只有一个解决方案**
**失败模式：** 列出一个功能，因为利益相关者已经决定了。

**后果：** 没有探索替代方案；无法测试哪个解决方案最好。

**修复：** 强迫自己列出3+个解决方案。问："还有什么可以解决这个问题？"

---

### 6. **跳过实验（格子8）**
**失败模式：** "我们将直接构建它，看看会发生什么。"

**后果：** 浪费数周/数月构建错误的事物。

**修复：** 首先设计最小实验。如果您想不出，使用 `skills/pol-probe-advisor/SKILL.md` 选择验证方法。
