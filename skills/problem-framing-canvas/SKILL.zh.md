## 目的

通过在三个阶段的结构化问题引导产品经理完成 MITRE 问题定义画布流程：向内看（审视你自己的假设和偏见）、向外看（理解谁经历了问题以及谁没有）、重新定义（将洞察综合为可执行的问题陈述和"我们如何能"问题）。用它来确保你在跳到解决方案之前解决正确的问题——避免确认偏见、被忽视的利益相关者和方案优先思维。

这不是解决方案头脑风暴——它是一个问题定义工具，拓宽视角、挑战假设，并产生清晰的、公平驱动的问题陈述。

## 关键概念

### 什么是 MITRE 问题定义画布？

问题定义画布（MITRE Innovation Toolkit，v3）是一个结构化框架，帮助团队在提出解决方案之前全面探索问题空间。它被划分为**三个区域**：

1. **向内看** — 审视你自己的假设、偏见，以及你如何可能成为问题的一部分
2. **向外看** — 理解谁经历了这个问题，谁从中受益，以及谁被排除在外
3. **重新定义** — 将洞察综合为清晰、可执行的问题陈述和"我们如何能"问题

### 画布结构

```
┌─────────────────────────────────────────────────────────────────┐
│ 向内看（LOOK INWARD）                                              │
│ - 问题是什么？（症状）                                            │
│ - 为什么我们还没有解决它？（新的、困难的、低优先级等）              │
│ - 我们如何成为问题的一部分？（假设、偏见）                          │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 向外看（LOOK OUTWARD）                                             │
│ - 谁经历了这个问题？何时/何地/后果？                               │
│ - 谁还有这个问题？谁没有？                                         │
│ - 谁被排除在外了？                                                 │
│ - 当问题存在/不存在时，谁受益？                                   │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ 重新定义（REFRAME）                                                 │
│ - 换句话说，问题在于：[重新陈述]                                   │
│ - 我们如何能 [行动]，以便我们能够达成 [目标]？                     │
└─────────────────────────────────────────────────────────────────┘
```

### 为什么这个方法有效
- **拓宽视角：** 迫使你超越自己的假设
- **公平驱动：** 以被边缘化的声音为中心，问"谁被排除在外了？"
- **挑战偏见：** 在定义问题之前要求明确审视假设
- **可执行输出：** 产生可供解决方案探索的 HMW 语句

### 反模式（这不是什么）
- **不是解决方案头脑风暴：** 画布定义问题；解决方案稍后出现
- **不是功能需求列表：** 关注底层问题，而非表面症状
- **不是单人练习：** 需要多样化视角来挑战群体思维

### 何时使用
- 开始新举措的发现
- 重新定义现有问题（怀疑你解决的是错误的事情）
- 在构建解决方案之前挑战假设
- 让跨职能团队在问题定义上对齐

### 何时不使用
- 当问题已经被很好理解和验证时
- 对于战术性 bug 修复或技术债务（不需要深度定义）
- 当利益相关者已经承诺了解决方案时（先解决对齐问题）

## 应用

使用 `template.md` 获取完整的填写结构。

这个互动式技能遵循**三阶段流程**，在每个阶段问**适应性问题**。

### 第 0 步：收集上下文（问题之前）

**Agent 建议：**

在我们定义你的问题之前，让我们收集上下文：

**问题上下文：**
- 最初的问题陈述或利益相关者请求
- 你观察到的症状（支持工单、流失数据、用户投诉）
- 现有研究（用户访谈、调查、分析）
- 你对问题做出的假设

**利益相关者上下文：**
- 谁受这个问题影响？（用户、客户、内部团队）
- 谁在要求解决这个问题？（高管、销售、客户）
- 谁可能被忽视了？

**你可以直接粘贴这些内容，或者简要描述问题。**

## 阶段 1：向内看

**目标：** 审视你自己的假设、偏见，以及你如何可能成为问题的一部分。

---

### 问题 1：问题是什么？（描述症状）

**Agent 问：**

"以你目前理解的，问题是什么？描述症状。"

**提供 4 个枚举选项：**

1. **客户痛点** — "客户在 [特定任务/结果] 方面很吃力"（例如，"客户找不到他们需要的功能"）
2. **业务指标问题** — "我们看到 [指标下降]"（例如，"上个季度流失增加了 15%"）
3. **利益相关者请求** — "利益相关者说我们需要 [功能/变更]"（例如，"销售团队说我们需要更好的报告"）
4. **观察到的行为** — "我们注意到 [模式/趋势]"（例如，"用户在第 3 步放弃入职"）

**或者描述你的问题/症状。**

**用户回答：** [选择或自定义]

**Agent 提取：**
- **问题（初步定义）：** [用户的描述]

---

### 问题 2：我们为什么还没有解决它？

**Agent 问：**

"为什么这个问题还没有被解决？"

**提供 6 个枚举选项（可以选择多个）：**

1. **这是新的** — "问题最近出现"
2. **这很困难** — "技术复杂或资源密集"
3. **这是低优先级** — "其他举措占了先"
4. **缺乏资源** — "预算、人员或时间不足"
5. **缺乏权威** — "无法做出决定或获得认同"
6. **系统性不公平** — "问题不成比例地影响边缘群体，被忽视"

**或者描述你自己的原因。**

**用户回答：** [选择或自定义]

**Agent 捕获：**
- **解决障碍：** [原因列表]

---

### 问题 3：我们如何成为问题的一部分？（假设和偏见）

**Agent 问：**

"你（或你的团队）如何可能成为问题的一部分？你带来了什么假设或偏见？"

**提供 4 个枚举选项：**

1. **假设我们知道客户想要什么** — "我们还没有用真实用户验证"（确认偏见）
2. **为我们自己而非用户优化** — "构建对我们来说容易的，而不是对他们有价值的"（内部偏见）
3. **忽视特定用户细分** — "专注于多数用户，忽视边缘情况或边缘群体"（幸存者偏差）
4. **方案优先思维** — "在理解根本问题之前就跳到'我们需要 [功能 X]'"（过早收敛）

**或者描述你具体的假设/偏见。**

**用户回答：** [选择或自定义]

**Agent 捕获：**
- **要挑战的假设：** [偏见列表]

## 阶段 2：向外看

**目标：** 理解谁经历了问题，谁从中受益，以及谁被排除在外。

---

### 问题 4：谁经历了这个问题？（何时、何地、后果）

**Agent 问：**

"谁经历了这个问题？他们何时何地经历它？他们面临什么后果？"

**Agent 提示用户描述：**
- **谁：** 具体的用户画像、用户细分或角色
- **何时：** 触发事件或上下文（例如，"入职期间"、"月末结账时"）
- **何地：** 物理或数字位置（例如，"移动应用"、"企业部署"）
- **后果：** 对用户的影响（例如，"每周浪费 2 小时"、"错过截止日期"、"流失"）

**调整：** 使用上下文中的用户画像（原型用户画像、JTBD、客户研究）

**用户回答：** [详细描述]

**Agent 捕获：**
- **谁经历了它：** [用户画像/细分]
- **何时/何地：** [上下文]
- **后果：** [影响]

### 问题 5：谁还有这个问题？谁没有？

**Agent 问：**

"谁还有这个问题？（同事、竞争对手、其他领域？）谁没有？"

**Agent 提示：**
- **谁还有：** 有类似问题的其他公司、行业或领域
- **他们如何处理它：** 变通方案、解决方案或适应
- **谁没有：** 避免问题的用户/公司（他们的不同之处是什么？）

**用户回答：** [详细描述]

**Agent 捕获：**
- **谁还有：** [例子]
- **谁没有：** [反例]

---

### 问题 6：谁被排除在外？谁受益？

**Agent 问：**

"到目前为止，谁被排除在对话之外？当这个问题存在或不存在时，谁受益？"

**Agent 提示：**
- **谁被排除在外：** 被边缘化的声音、边缘情况、被忽视的利益相关者
- **当问题存在时谁受益：** 谁从现状中获益？
- **当问题不存在时谁受益：** 如果问题被解决，谁会失去？

**示例：**
- "当入职流程坏掉时，谁受益？" → "销售团队不必支持复杂工作流；工程不必构建引导流程"
- "谁被排除在外？" → "非技术用户、国际客户（入职仅提供英语）"

**用户回答：** [详细描述]

**Agent 捕获：**
- **谁被排除在外：** [列表]
- **谁受益（问题存在时）：** [列表]
- **谁受益（问题解决时）：** [列表]

### 问题 7：重新陈述问题

**Agent 说：**

"基于我们探索的一切，让我们以一种新的方式重新陈述问题。"

**Agent 使用阶段 1-2 的洞察生成精炼的问题陈述：**

**模板：**
"问题在于：[谁] 在 [完成什么] 方面很吃力，因为 [根本原因]，这导致 [后果]。这影响了 [特定细分]，并且一直被忽视，因为 [来自阶段 1 的偏见/假设]。"

**示例（SaaS 入职）：**
"问题在于：非技术型小企业主在我们的产品入职激活过程中很吃力，因为我们使用术语密集的 UI 且缺乏引导式工作流，这导致 60% 在 24 小时内放弃。这不成比例地影响了没有技术支持的个体创业者，并且一直被忽视，因为我们的团队为企业用户优化，他们有 IT 部门。"

**Agent 问：**

"这个重新陈述捕捉到核心问题了吗？我们应该细化它吗？"

**用户回答：** [批准或修改]

**Agent 说：**

"现在让我们用'我们如何能'语句使其可执行。"

"我们如何能 [解决这个问题的行动]，以便我们能够达成 [目标/期望状态]？"

"我们如何能在入职过程中用直白语言提示引导非技术用户，以便我们将激活率从 40%提高到 70%？"

## 常见陷阱

### 陷阱 1：跳过"向内看"（假设你是中立的）
**症状：** 团队在没有审视偏见的情况下直接跳到"向外看"

**后果：** 群体思维持续，假设未被挑战

**修复：** 强制进行假设和偏见的明确讨论（Q2-Q3）

---

### 陷阱 2：忽视"谁受益"问题
**症状：** 完成画布时没有探索谁从问题存在中受益

**后果：** 错过政治动态和对变革的阻力

**修复：** 始终问"如果这个问题被解决，谁会失去？"（Q6）

---

### 陷阱 3：通用问题陈述
**症状：** 重新定义的问题是模糊的（"改善用户体验"）

**后果：** HMW 语句不可执行

**修复：** 使问题具体化（谁、什么、何时、后果、根本原因）

---

### 陷阱 4：HMW 语句太窄
**症状：** "我们如何能添加一个移动应用？"

**后果：** 将解决方案空间限制为一个想法

**修复：** 保持 HMW 广泛："我们如何能让移动优先用户在任何设备上访问核心工作流？"

---

### 陷阱 5：单人练习（没有多样化视角）
**症状：** PM 独自填写画布

**后果：** 偏见持续，被边缘化的声音仍然被排除

**修复：** 与跨职能团队 + 客户输入引导画布工作坊
