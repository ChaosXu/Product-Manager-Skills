## 目的
指导产品经理通过从利益相关者请求中提取目标成果、生成机会选项（要解决的问题）、映射潜在解决方案以及基于可行性、影响和市场契合度选择最佳概念验证（POC）来创建机会解决方案树（OST）。使用此技能将模糊的产品请求转变为结构化发现，确保团队在跳到解决方案之前解决正确的问题——避免"功能工厂"综合症和想法的过早收敛。

这不是路线图生成器——它是一个结构化发现过程，输出带有可测试解决方案假设的已验证机会。

## 关键概念

### 什么是机会解决方案树（OST）？

OST是一个可视化框架（Teresa Torres，《*持续发现习惯*》），连接：
1. **期望成果**（业务目标或产品指标）
2. **机会**（可能推动成果的客户问题、需求、痛点或愿望）
3. **解决方案**（解决每个机会的方法）
4. **实验**（验证解决方案的测试）

**结构：**
```
          期望成果 (1)
                 |
     +-----------+-----------+
     |           |           |
 机会          机会          机会 (3)
     |           |           |
   +-+-+       +-+-+       +-+-+
   | | |       | | |       | | |
  S1 S2 S3    S1 S2 S3    S1 S2 S3 (9个解决方案)
```

### 为什么这有效
- **成果驱动：** 从业务目标而非功能请求开始
- **先发散后收敛：** 在选择解决方案之前探索多个机会
- **问题聚焦：** 机会是问题，而非伪装成问题的解决方案
- **可测试：** 每个解决方案都映射到实验，而非仅仅是"构建并发布"
- **POC选择：** 在投入资源之前评估可行性、影响、市场契合度

### 反模式（这不是什么）
- **不是功能列表：** 机会是客户面临的问题，而非"我们需要深色模式"
- **不是解决方案优先：** 不要从"我们应该构建X"开始——从"客户在Y方面有困难"开始
- **不是瀑布规划：** OST是发现工具，而非项目计划
- **不是一次性练习：** OST随着从实验中的学习而演变

### 何时使用
- 利益相关者请求功能或产品举措
- 开始新产品领域的发现
- 澄清模糊的OKR或战略目标
- 优先排序要首先解决的问题
- 对齐团队正在推动的成果

### 何时不使用
- 问题已经验证时（转向解决方案测试）
- 战术性错误修复或技术债务（不需要发现）
- 利益相关者要求特定解决方案时（首先解决对齐问题）

## 应用

使用 `template.md` 获取完整的填写结构。

此交互式技能遵循**两阶段过程**：

**阶段1：** 生成OST（提取成果、识别机会、映射解决方案）
**阶段2：** 选择POC（评估解决方案、推荐最佳起点）

## 阶段1：生成机会解决方案树

### 问题1：提取期望成果

**Agent提问：**
"这个举措的期望成果是什么？（您正在努力推动什么业务或产品指标？）"

**提供4个编号选项：**

1. **收入增长** — "增加ARR、扩大现有客户收入、新收入流"（规模化产品的常见选择）
2. **客户留存** — "减少流失、增加激活、改善参与度/粘性"（有留存问题的成熟产品的常见选择）
3. **客户获取** — "增加注册、试用转化、新用户增长"（早期或增长产品的常见选择）
4. **产品效率** — "减少支持成本、缩短价值实现时间、改善运营指标"（优化运营的成熟产品的常见选择）

**或者描述您特定的期望成果（可衡量：例如，"将试用到付费转化率从15%提高到25%"）。**

**用户响应：** [选择或自定义]

**Agent提取并确认：**
- **期望成果：** [具体、可衡量的成果]
- **为什么重要：** [来自利益相关者请求或上下文的理由]

---

### 问题2：识别机会（要解决的问题）

**Agent根据提供的期望成果和上下文生成3个机会。**

**Agent说：**
"根据您的期望成果（来自问题1）和您提供的上下文，这里是**3个机会**（客户问题或需求），可能推动这个成果："

**示例（如果成果 = 增加试用到付费转化）：**

1. **机会1：用户在试用期间没有体验到价值** — "新用户注册但不完成入职，永远达不到'aha时刻'，在看到核心价值前放弃"
   - 证据：[来自上下文：入职分析、支持工单、退出调查]

2. **机会2：定价不清晰或不对齐** — "用户不确定付费计划是否值得；不理解他们付的价格得到什么；定价页面令人困惑"
   - 证据：[来自上下文：定价页面漏斗流失、销售异议]

3. **机会3：免费计划'足够好'** — "用户无限期地保持在免费层，因为它满足他们的需求；没有令人信服的升级理由"
   - 证据：[来自上下文：免费增值用户留存数据、询问变通方案的支持工单]

**Agent提问：**
"哪个机会感觉最关键需要首先探索，或者您想修改/添加机会？"

**用户响应：** [选择或自定义]

---

### 问题3：为选定机会生成解决方案

**Agent为选定机会生成3个解决方案想法。**

**Agent说：**
"对于**机会[X]：[名称]**，这里是**3个潜在解决方案**来测试："

**示例（如果选择机会1：用户在试用期间没有体验到价值）：**

1. **解决方案1：引导式入职清单** — "互动清单，逐步引导用户完成核心工作流（例如，'创建您的第一个项目'、'邀请队友'、'完成任务'）"
   - 假设：结构化指导提高完成率
   - 实验：A/B测试清单vs无清单，衡量激活率

2. **解决方案2：价值实现时间触发器** — "当用户卡住时自动提示（例如，'您还没有创建项目——这里有一个模板可以帮助您开始'）"
   - 假设：主动提示防止流失
   - 实验：跟踪提示参与度，衡量试用到付费的提升

3. **解决方案3：人工辅助入职** — "为高价值试用用户（企业、团队计划）提供15分钟与CSM的入职电话"
   - 假设：个人接触提高高意图用户的转化
   - 实验：提供给50个试用用户，衡量转化vs对照组

**Agent提问：**
"您想探索其他机会的解决方案，还是进入POC选择？"

**用户响应：** [选择或自定义]

## 阶段2：选择概念验证（POC）

在生成解决方案后，Agent帮助选择首先测试哪个解决方案。

---

### 问题4：评估解决方案（可行性、影响、市场契合度）

**Agent说：**
"让我们评估您的解决方案以选择最佳起点。我将根据**可行性**（构建难度）、**影响**（可能推动成果的程度）和**市场契合度**（与客户需求的对齐程度）为每个解决方案打分。"

**Agent生成评估表：**

| 解决方案 | 可行性 (1-5) | 影响 (1-5) | 市场契合度 (1-5) | 总分 | 理由 |
|----------|--------------|------------|------------------|------|------|
| 解决方案1：引导式入职清单 | 4 | 4 | 5 | 13 | 高可行性（UI模式）、已验证影响（行业标准）、强市场契合度（用户期望入职） |
| 解决方案2：价值实现时间触发器 | 3 | 3 | 4 | 10 | 中等可行性（需要分析集成）、中等影响（取决于触发器质量）、良好市场契合度 |
| 解决方案3：人工辅助入职 | 5 | 5 | 3 | 13 | 高可行性（无需开发工作）、高影响（个人接触）、较低市场契合度（不能扩展，仅高接触） |

**评分标准：**
- **可行性：** 1 = 数月工作，5 = 天/周
- **影响：** 1 = 最小成果移动，5 = 主要成果转变
- **市场契合度：** 1 = 客户不关心，5 = 客户主动请求这个

**Agent推荐：**

**推荐POC：解决方案1（引导式入职清单）**

**为什么这个POC：**
- 在可行性（可以在2-4周内构建）和影响（已验证模式）之间取得平衡
- 强市场契合度（用户期望入职指导）
- 可测试假设："如果我们将用户引导完成核心工作流，激活率将从X%提高到Y%"

**替代POC：** 解决方案3（人工辅助入职）
- 如果您想无需开发工作快速学习，从这里开始
- 手动运行20-50个试用用户，收集定性反馈
- 使用学习来为自动化解决方案提供信息（解决方案1）

**不推荐作为POC：** 解决方案2（价值实现时间触发器）
- 需要更多前期投入
- 影响取决于触发器质量（需要实验才能正确）
- 在验证核心入职流程后作为后续更好

---

### 问题5：定义实验

**Agent提问：**
"您将如何测试这个解决方案？什么是实验？"

**提供3个编号选项：**

1. **A/B测试** — "构建MVP，展示给50%的试用用户，比较转化vs对照组"（最适合：定量验证、需要流量）
2. **原型+可用性测试** — "创建可点击原型，观察10个用户尝试入职，收集定性反馈"（最适合：早期验证、低流量）
3. **手动礼宾测试** — "手动运行20个用户的解决方案（例如，亲自引导他们完成入职），衡量成果"（最适合：快速学习、无需开发工作）

**或者描述您的实验方法。**

**用户响应：** [选择或自定义]

## 常见陷阱

### 陷阱1：伪装成解决方案的机会
**症状：** "机会：我们需要一个移动应用"

**后果：** 您在没有探索问题的情况下已经收敛到解决方案。

**修复：** 将机会重新框定为客户问题："移动优先用户无法在外出时访问产品。"

---

### 陷阱2：跳过发散（跳到单一解决方案）
**症状：** "我们知道解决方案是[X]，只需要构建它"

**后果：** 错过更好的替代方案，没有学习。

**修复：** 每个机会至少生成3个解决方案。在收敛之前强制发散。

---

### 陷阱3：成果太模糊
**症状：** "期望成果：改善用户体验"

**后果：** 无法衡量成功，无法优先排序机会。

**修复：** 使成果可衡量："将NPS从30提高到50"或"将入职流失从60%减少到40%。"

---

### 陷阱4：没有实验（只是构建它）
**症状：** 选择解决方案后直接进入路线图

**后果：** 没有验证，构建错误事物的高风险。

**修复：** 每个解决方案必须映射到实验。没有实验 = 没有OST。

---

### 陷阱5：分析瘫痪（永远探索）
**症状：** 生成20个机会、50个解决方案，从不选择任何一个

**后果：** 团队陷入发现，没有进展。

**修复：** 限制为3个机会，每个3个解决方案（共9个）。选择POC，运行实验，学习，迭代。
