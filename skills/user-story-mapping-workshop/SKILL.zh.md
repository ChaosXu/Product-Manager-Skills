## 目的

通过关于系统、用户、工作流和优先级的适应性问题，引导产品经理创建用户故事地图——然后生成包含骨架（活动）、用户任务和发布切片的二维地图。用它来从扁平待办列表转向可视化故事地图，传达全局、识别缺失功能并实现有意义的发布计划——避免"上下文无关的覆盖物"，即故事失去与整体系统叙事的联系。

这不是待办生成器——而是一个可视化沟通框架，按用户工作流（水平）和优先级（垂直）组织工作。

## 关键概念

### 什么是用户故事地图？

故事地图（Jeff Patton）按**两个维度**组织用户故事：

**水平轴（从左到右）：** 按叙事/工作流顺序排列的活动——这是你向别人解释系统时使用的顺序

**垂直轴（从上到下）：** 每个活动内的优先级，最重要的任务在最上面

**结构：**
```
骨架（顶部的活动）
↓
用户任务（按优先级垂直下降）
↓
细节/验收标准（在底部）
```

### 关键原则

**骨架：** Essential 活动形成系统的结构核心——这些不会相互比较优先级；它们是叙事流程。

**行走骨架：** 所有活动中最高优先级的任务形成最小可行产品——最小端到端功能。

**肋骨：** 支持性任务在每个活动下垂直下降，通过位置表示优先级。

**从左到右、从上到下的构建策略：** 在所有主要功能上增量构建，而不是在开始另一个功能之前完成一个功能的全部。

### 为什么这个方法有效
- **可视化沟通：** 故事地图保持显示作为信息辐射器，维持对全局的关注
- **叙事结构：** 按用户工作流组织，而非技术架构
- **发布计划：** 水平切片揭示 MVP 和增量发布
- **识别缺口：** 揭示扁平待办列表掩盖的缺失功能

### 反模式（这不是什么）
- **不是甘特图：** 故事地图显示优先级，不显示时间估算
- **不是技术架构：** 地图遵循用户工作流，而非系统层（UI → API → DB）
- **不是项目计划：** 它是发现和沟通工具，不是时间表

### 何时使用
- 启动新产品或主要功能
- 重新构建现有待办列表（从扁平列表转向可视化地图）
- 让利益相关者对齐范围和优先级
- 计划 MVP 或增量发布

### 何时不使用
- 单功能项目（故事地图过度设计）
- 当待办列表已经被很好地理解和优先排序时
- 对于技术重构工作（没有用户工作流可映射）

## 应用

这个互动式技能问 **最多 5 个适应性问题**，在每一步提供 **3-4 个枚举选项**。

使用 `template.md` 获取引导议程和输出检查清单。

交互模式：当你想要一次一步的流程、在决策点有编号建议、在常规问题有快速选择选项时，与 `skills/workshop-facilitation/SKILL.md` 配对使用。如果用户请求单次输出，跳过多轮引导。

### 第 0 步：收集上下文（问题之前）

**Agent 建议：**

在我们创建你的故事地图之前，让我们收集上下文：

**产品/功能上下文：**
- 你要映射的是什么系统或功能？
- 产品概念、PRD 草稿或现有待办列表
- 网站文案、定位材料或用户流程
- 现有用户故事（如果从扁平待办列表转换）

**用户上下文：**
- 目标用户画像或用户细分
- 用户研究、访谈或旅程地图
- 待完成工作或问题陈述

**你可以直接粘贴这些内容，或者简要描述系统。**

---

### 问题 1：定义范围

**Agent 问：**

"你要映射什么？（范围是什么？）"

**提供 4 个枚举选项：**

1. **整个产品** — "从发现到完成的完整端到端系统"（对于新产品或完全重写很常见）
2. **主要功能区域** — "较大产品内的特定工作流（例如'入职'、'结账'、'报告'）"（对于功能发布很常见）
3. **用户旅程** — "特定用户目标或待完成工作（例如'雇佣承包商'、'报税'）"（对于 JTBD 驱动的映射很常见）
4. **重新设计/重构** — "正在重建或简化的现有产品/功能"（对于遗留系统现代化很常见）

**或者描述你的具体范围。**

**用户回答：** [选择或自定义]

---

### 问题 2：识别用户/用户画像

**Agent 问：**

"这个地图的主要用户是谁？（列出用户画像或用户细分。）"

**提供 4 个枚举选项：**

1. **单一用户画像** — "一种主要用户类型（例如'小企业主'）"（简化映射，适合 MVP）
2. **多个用户画像，共享工作流** — "不同的用户类型，相同的核心活动（例如'买家'和'卖家'都在浏览列表'）"（对于市场平台很常见）
3. **多个用户画像，不同工作流** — "具有不同工作流的不同用户类型（例如'管理员' vs '最终用户'）"（需要单独的地图或泳道）
4. **组织内角色** — "不同的岗位职能（例如'PM'、'设计师'、'工程师'）"（对于内部工具很常见）

**或者描述你的用户。**

**调整：** 使用第 0 步提供的上下文中的用户画像（原型用户画像、JTBD 等）

**用户回答：** [选择或自定义]

---

### 问题 3：生成骨架（活动）

**Agent 说：**

"让我们构建骨架——用户为实现目标而执行的活动叙事流程。"

**Agent 根据范围（Q1）和用户（Q2）生成 5-8 个活动**，从左到右按工作流顺序排列。

**示例（范围 = "电商结账"）：**

```
骨架活动（从左到右）：

1. 浏览产品
2. 加入购物车
3. 查看购物车
4. 输入配送信息
5. 输入支付信息
6. 确认订单
7. 收到确认
```

**Agent 问：**

"这个骨架是否捕捉到了完整的工作流？我们应该添加、删除或重新排序活动吗？"

**用户回答：** [批准、修改或添加自定义活动]

---

### 问题 4：生成用户任务（每个活动下）

**Agent 说：**

"现在让我们在每个活动下添加用户任务，按优先级组织（顶部 = 必须有，底部 = 最好有）。"

**Agent 每个活动生成 3-5 个用户任务**，按优先级垂直排列。

**示例（活动 2："加入购物车"）：**

```
加入购物车（活动）
├─ 将单个商品加入购物车（必须有，行走骨架）
├─ 调整数量（必须有）
├─ 一次添加多个商品（应该有）
├─ 保存以便稍后（最好有）
└─ 添加礼品包装（最好有）
```

**Agent 为所有骨架活动重复**，显示完整地图。

**Agent 问：**

"这是否捕捉到了关键任务？优先级正确吗（顶部 = MVP，底部 = 后续发布）？"

**用户回答：** [批准、修改或添加自定义任务]

---

### 问题 5：识别发布切片（行走骨架 + 增量）

**Agent 说：**

"让我们通过在地图上画水平线来定义发布切片。"

**Agent 生成 3 个发布切片：**

**发布 1（行走骨架）：** 所有活动中的最高优先级任务——最小的端到端功能

**发布 2（下一个增量）：** 增强核心工作流的第二优先级任务

**发布 3（完善/扩展）：** 第三优先级任务（最好有、边缘情况、优化）

**示例：**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
发布 1（行走骨架）：
- 浏览产品（基本列表视图）
- 将单个商品加入购物车
- 查看购物车（商品明细 + 总计）
- 输入配送信息（姓名、地址）
- 输入支付信息（仅信用卡）
- 确认订单（基本确认）
- 收到邮件确认
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
发布 2（增强）：
- 产品筛选/搜索
- 在购物车中调整数量
- 保存以便稍后
- 多种配送选项
- 多种支付方式
- 订单跟踪链接
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
发布 3（完善）：
- 产品推荐
- 游客结账
- 礼品包装
- 促销代码
- 高级支付选项
- 购后调查
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**Agent 问：**

"这些发布切片合理吗？我们应该调整范围或优先级吗？"

**用户回答：** [批准或修改]

## 示例

### 示例 1：好的故事地图（电商结账）

**Q1 回答：** "主要功能区域 — 电商结账工作流"

**Q2 回答：** "单一用户画像 — 在线购物者"

**Q3 - 生成的骨架：**
```
浏览 → 加入购物车 → 查看购物车 → 输入配送 → 输入支付 → 确认 → 收到确认
```

**Q4 - 生成的用户任务：**

```
浏览产品
├─ 查看产品列表（R1）
├─ 搜索/筛选（R2）
└─ 产品推荐（R3）

加入购物车
├─ 添加单个商品（R1）
├─ 调整数量（R2）
└─ 保存以便稍后（R3）

查看购物车
├─ 查看商品明细 + 总计（R1）
├─ 使用促销代码（R2）
└─ 估算运费（R3）

[...等等...]
```

**Q5 - 发布切片：**
- **发布 1：** 行走骨架——无附加功能的基本流程
- **发布 2：** 搜索、数量调整、促销代码
- **发布 3：** 推荐、游客结账、礼品选项

**为什么有效：**
- 骨架遵循用户叙事（而非技术层）
- 行走骨架交付端到端价值
- 增量发布在不破坏核心流程的情况下增加复杂性

---

### 示例 2：坏的故事地图（技术层）

**骨架（错误）：**
```
UI 层 → API 层 → 数据库层 → 部署
```

**为什么失败：**
- 不是以用户为中心（用户不关心技术架构）
- 无法增量交付端到端价值
- 伪装成故事映射的瀑布思维

**修复：**
- 按用户工作流映射："注册 → 配置设置 → 邀请团队 → 启动项目"
- 每个发布交付完整工作流，而非单一层

## 常见陷阱

### 陷阱 1：伪装成扁平待办列表
**症状：** 故事地图只是垂直列表，没有水平叙事

**后果：** 失去沟通效益；仍是"上下文无关的覆盖物"

**修复：** 强制水平结构——活动在顶部，任务垂直下降

---

### 陷阱 2：以技术架构作为骨架
**症状：** 骨架 = "前端 → 后端 → 数据库"

**后果：** 不是以用户为中心，无法增量交付价值

**修复：** 骨架应该遵循用户工作流，而非系统层

---

### 陷阱 3：功能完整的瀑布
**症状：** 发布 1 = "完全构建活动 1"，发布 2 = "完全构建活动 2"

**后果：** 在所有活动完成之前没有端到端价值

**修复：** 行走骨架 = 跨越所有活动的薄切片，逐步增强

---

### 陷阱 4：过早过多细节
**症状：** 试图一开始就映射每个边缘情况和验收标准

**后果：** 分析瘫痪，失去全局

**修复：** 从骨架 + 高层任务开始，后续细化

---

### 陷阱 5：地图藏在工具中
**症状：** 故事地图存在于 Jira/Miro 中，从不展示

**后果：** 失去作为信息辐射器的价值

**修复：** 打印/张贴地图实物；让团队日常可见
