# 高度-视野框架示例

此文件展示了如何在真实的 PM 到 Director 转型场景中应用该框架。

---

## 示例 1：好使用级联上下文图

### 场景

CEO 的公司优先事项："今年赢得更大的企业交易。"

一位新晋升的 Director 有三位 PM 问："这对我们的季度路线图意味着什么？"

### 完成的上下文级联

```markdown
## 上下文级联

**公司优先事项：** 今年赢得更大的企业交易。

**业务单元翻译：** 提高平均合同价值，减少企业客户安全审批时间。

**产品组合翻译：**
- 产品 A：加强管理控制和角色权限
- 产品 B：改进 API 文档和集成可靠性
- 产品 C：弥补 SOC 2 和 SSO 采用差距

**团队责任：**
- 团队 A 负责管理控制和审计日志
- 团队 B 负责 API 文档、SDK 质量和集成示例
- 团队 C 负责安全认证和 SSO 实施质量

**为什么这很重要：**
企业增长不意味着"构建随机企业功能。"
它意味着消除阻碍企业交易和采购的障碍。
```

### 为什么这是强有力的

- 将模糊的战略转化为具体的团队所有权。
- 保持高度：首先是产品组合和成果，其次是待办事项细节。
- 使权衡可见：现在改变什么 vs. 稍后改变什么。

## 示例 2：反模式（英雄综合症）

### 场景

一位 PM 就路线图承诺与销售发生冲突而升级。

### Director 回应（弱）

"我会加入客户电话并为你处理这件事。"

### Director 回应（强）

"告诉我你目前的框架。我会辅导你的下一步，然后你主导对话。"

### 为什么第一个回应失败

- 解决了即时痛苦但强化了依赖。
- 将 Director 保持在 PM 级别的冲突解决中。
- 阻止了 PM 在利益相关者领导力上的成长。

### 更好的跟进

1. 汇报 PM 的框架。
2. 确认一个明确的信息和一个后备立场。
3. 让 PM 主导，Director 支持。
4. 通话后：确定下次改进的一个行为。

---

## 示例 3：高度校准检查

在重大决策之前使用此快速自我审计：

- 我是在团队/待办事项高度还是产品组合高度做决定？
- 在我当前的职责层级，谁应该拥有这个决定？
- 如果我介入，我是在建立系统清晰度还是在救援执行？
- 团队现在缺少什么上下文翻译？

如果大多数答案指向执行救援，你可能正在滑入英雄综合症。
