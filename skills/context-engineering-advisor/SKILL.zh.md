## 目的

指导产品经理诊断他们是在做**上下文填充**（无目的地塞入大量内容）还是**上下文工程**（为注意力塑造结构）。用它来识别上下文边界、修复"上下文囤积症"，并实施像有界领域、情景检索和研究→计划→重置→实施循环这样的战术实践。

**关键区别：** 上下文填充假设容量 = 质量（"粘贴整个PRD"）。上下文工程将AI注意力视为稀缺资源并有意识地分配。

这不是关于提示词写作——而是关于**设计信息架构**，使AI扎根于现实而不被噪音淹没。

## 关键概念

### 范式转变：参数智能 → 上下文智能

**根本问题：**

- LLM有**参数知识**（训练时编码）= 静态、过时、不可归因
- 当被问及专有数据、实时信息或用户偏好时 → 被迫产生幻觉或承认无知
- **上下文工程**弥合了静态训练和动态现实之间的差距

**PM的角色转变：** 从功能构建者 → **信息生态系统的架构师**，使AI扎根于现实

---

### 上下文填充 vs. 上下文工程

| 维度 | 上下文填充 | 上下文工程 |
|------|------------|------------|
| **心态** | 容量 = 质量 | 结构 = 质量 |
| **方法** | "以防万一添加一切" | "我要做什么决定？" |
| **持久性** | 持久化所有上下文 | 有意图地检索 |
| **Agent链** | Agent之间共享一切 | 每个Agent有有界上下文 |
| **失败响应** | 重试直到成功 | 修复结构 |
| **经济模型** | 上下文作为存储 | 上下文作为注意力（稀缺资源） |

**关键隐喻：** 上下文填充就像带着整个文件柜去开会。上下文工程只带3份与今天决定相关的文件。

---

### 反模式：上下文填充

**上下文填充的五个标志：**

1. **反射性地扩展上下文窗口** — "只需添加更多token！"
2. **持久化一切"以防万一"** — 没有明确的保留标准
3. **无边界地链接Agent** — Agent A传递给Agent B再传递给Agent C
4. **添加评估来掩盖不一致** — "我们只需重试直到正确"
5. **重试正常化** — "运行3次就能工作"变得可接受

**为什么失败：**

- **推理噪音：** 数千个不相关文件争夺注意力，破坏多跳逻辑
- **上下文腐烂：** 死胡同、过去错误、不相关数据积累 → 目标漂移
- **中间丢失：** 模型优先处理开头（首因效应）和结尾（近因效应），忽略中间
- **经济浪费：** 每个查询都变得昂贵而没有准确性提升
- **定量降级：** 当上下文超过约32k token时，准确率降至20%以下

**隐藏成本：**

- 不断上升的token消耗
- 注意力在不相关材料上被稀释
- 输出信心降低
- 级联重试浪费时间和金钱

---

### 真正的上下文工程：核心原则

**五个基本原则：**

1. **没有形状的上下文变成噪音**
2. **结构 > 容量**
3. **有意图地检索，而非完整性**
4. **小工作上下文**（像短期记忆）
5. **上下文压缩：** 最大化每个token的相关信息密度

**定量框架：**
```
效率 = (准确度 × 连贯性) / (Token × 延迟)
```

**关键发现：** 使用RAG但只占用25%的可用token，可以保持95%的准确率，同时显著降低延迟和成本。

---

### 5个诊断问题（检测上下文囤积症）

用这些问题来识别上下文填充：

1. **这支持什么具体决定？** — 如果你无法回答，你不需要它
2. **检索可以替代持久化吗？** — 即时获取优于总是可用
3. **谁拥有上下文边界？** — 如果没有，边界会永远增长
4. **如果我们排除这个，什么会失败？** — 如果什么都没有破坏，删除它
5. **我们是在修复结构还是避免它？** — 填充上下文通常掩盖糟糕的信息架构

---

### 记忆架构：双层系统

**短期（对话）记忆：**

- 用于跟进问题的即时交互历史
- 挑战：空间管理 → 较旧部分被总结或截断
- 生命周期：单个会话

**长期（持久）记忆：**

- 跨会话的用户偏好、关键事实 → 深度个性化
- 通过向量数据库实现（语义检索）
- 两种类型：
  - **陈述性记忆：** 事实（"我是素食主义者"）
  - **程序性记忆：** 行为模式（"我通过首先检查日志来调试"）
- 生命周期：跨会话持久化

**LLM驱动的ETL：** 模型通过识别信号、与现有数据整合、自动更新数据库来生成自己的记忆。

---

### 研究 → 计划 → 重置 → 实施循环

**上下文腐烂解决方案：**

1. **研究：** Agent收集数据 → 大型、混乱的上下文窗口（噪音 + 死胡同）
2. **计划：** Agent综合成高密度SPEC.md或PLAN.md（真实来源）
3. **重置：** **清除整个上下文窗口**（防止上下文腐烂）
4. **实施：** 使用**仅**高密度计划作为上下文的新鲜会话

**为什么有效：** 上下文腐烂被消除；Agent以压缩的、高信号上下文干净地开始。

---

### 反模式（这不是什么）

- **不是关于选择AI工具** — Claude vs. ChatGPT不重要；架构重要
- **不是关于写更好的提示词** — 这是系统设计，不是文案写作
- **不是关于添加更多token** — "无限上下文"叙事是营销，不是工程现实
- **不是关于取代人类判断** — 上下文工程放大了判断，而不是消除它

---

### 何时使用此技能

✅ **使用当：**

- 你在将整个PRD/代码库粘贴到AI中却得到模糊响应时
- AI输出不一致（有时工作，有时不）
- 你在燃烧token而没有看到准确性提升
- 你怀疑自己在"上下文填充"但不知道如何修复
- 你需要为AI产品功能设计上下文架构

❌ **不使用当：**

- 你刚接触AI（首先从基本提示词开始）
- 你在寻找工具建议（这是关于架构，不是工具）
- 你的AI使用工作正常（如果没坏，不要修）

### 步骤0：收集背景

**Agent提问：**

在我们诊断你的上下文实践之前，让我们收集信息：

**当前AI使用：**

- 你使用什么AI工具/系统？（ChatGPT、Claude、自定义Agent等）
- 你用AI做什么PM任务？（PRD写作、用户研究综合、发现等）

- 尽管提供了"所有上下文"，响应是否模糊或含糊？

**系统架构（如适用）：**

- 你有自定义AI Agent或工作流吗？
- Agent之间如何共享上下文？
- 你使用RAG、向量数据库或记忆系统吗？

**你可以简要描述或粘贴示例。**

### 步骤1：诊断上下文填充症状

**Agent提问：**

让我们评估你是否正在经历**上下文填充**。你认可以下哪些症状？

**选择所有适用的：**

1. **"我将整个文档粘贴到AI中"** — 完整的PRD、完整的用户访谈记录、整个代码库
2. **"尽管有'所有上下文'，AI给出模糊、含糊的响应"** — 诸如"这取决于"、"考虑这些选项"、不明确的回复
3. **"我需要重试提示词3+次才能获得可用输出"** — 不一致性正常化
4. **"Token成本上升但准确性没有改善"** — 花更多，得到相同或更差的结果
5. **"我不断添加更多上下文希望它会有帮助"** — 没有策略的反射性扩展
6. **"我的Agent彼此传递一切"** — Agent A → Agent B → Agent C，完整上下文链
7. **"我没有明确的包含/排除标准"** — 没有上下文边界定义
8. **"以上都不是——我的AI使用正常工作"** — 跳转到高级优化

**用户回答：** [选择症状]

**Agent分析：**

根据你的选择：

- **0-1个症状：** 健康的上下文实践；继续优化
- **2-3个症状：** 早期上下文填充；在扩大规模之前解决
- **4+个症状：** 活跃的上下文囤积症；需要立即干预

**Agent继续诊断问题。**

---

### 步骤2：诊断问题1 — 这支持什么具体决定？

**Agent提问：**

让我们从最关键的问题开始：**对于你包含的每个上下文片段，它支持什么具体决定？**

**示例上下文分析：**

想象你要求AI"帮助发现规划"。你提供了：

- 整个PRD（20页）
- 50个用户访谈记录（完整）
- 竞争分析文档（15页）
- 过去3个月的团队会议笔记

**问题：** 你现在正在做什么决定？

**提供3个场景：**

1. **"我在决定首先面试哪个用户细分"**
   - **需要的上下文：** PRD中的用户细分（2段）、先前访谈主题（1页综合），不是完整记录
   - **不需要的上下文：** 会议笔记、完整竞争分析、完整PRD

2. **"我在决定在访谈中问哪些发现问题"**
   - **需要的上下文：** 研究目标（来自PRD）、过去访谈洞察（综合）、待完成工作框架
   - **不需要的上下文：** 完整竞争分析、完整会议笔记

3. **"我不确定我在做什么决定——我只是想让AI'理解我的产品'"**
   - **问题：** 没有具体决定 = 上下文填充陷阱
   - **修复：** 首先定义决定，然后选择上下文

**Agent建议：**

**最佳实践：** 在添加上下文之前，完成这个句子：
> "我需要这个上下文，因为我正在决定[具体决定]，如果没有[具体信息]，我无法做出那个决定。"

如果你无法完成那个句子，你不需要上下文。

**用户回答：** [描述他们的决定 + 上下文]

**Agent验证：** 上下文是否直接支持所述决定？如果不是，建议修剪。

---

### 步骤3：诊断问题2 — 检索可以替代持久化吗？

**Agent提问：**

**第二个问题：这是你总是需要的信息，还是可以即时检索的东西？**

**区别：**

**总是需要（持久化）：**

- 核心产品约束（技术、法规、战略）
- 适用于每个交互的用户偏好
- 关键定义（操作术语表）
- 不可协商的规则

**情景式（按需检索）：**

- 项目特定细节（这个Epic、这个Sprint）
- 历史数据（过去的PRD、旧访谈记录）
- 上下文事实（竞争分析、市场研究）
- 临时决定

**关键洞察：** 即时检索优于总是可用。不要持久化你可以检索的东西。

**提供3个选项：**

1. **"我的大部分上下文是总是需要的（核心约束、用户偏好）"**
   - **评估：** 好直觉；用问题4验证（如果排除什么会失败？）
   - **建议：** 构建约束注册表和操作术语表（持久化这些）

2. **"我的大部分上下文是情景式的（项目细节、历史数据）"**
   - **评估：** RAG或检索的完美候选
   - **建议：** 实现语义搜索；为每个查询只检索相关块

3. **"我不确定哪个是哪个——我为了安全持久化一切"**
   - **评估：** 经典上下文囤积症症状
   - **修复：** 对每个上下文片段应用问题4测试

**Agent建议：**

**经验法则：**

- **持久化：** 在80%+交互中引用的信息
- **检索：** 在<20%交互中引用的信息
- **灰色地带（20-80%）：** 取决于检索延迟 vs. 上下文窗口成本

**用户回答：** [分类他们的上下文]

**Agent提供：** 关于什么持久化 vs. 什么检索的具体建议。

---

### 步骤4：诊断问题3 — 谁拥有上下文边界？

**Agent提问：**

**第三个问题：谁负责定义你的AI上下文的内外边界？**

**所有权问题：**

如果**没有人**拥有上下文边界，它将无限增长。每个PM都会添加"再来一件事"，六个月后，你每个查询填充100k token。

**提供3个选项：**

1. **"我拥有边界（独立PM或小团队）"**
   - **评估：** 好——你可以快速决策
   - **建议：** 记录你的边界标准（使用问题1-5作为框架）

2. **"我的团队共享所有权（协作边界定义）"**
   - **评估：** 如果正式化可以工作
   - **建议：** 创建"上下文清单"文档：什么总是包含、什么检索、什么排除（以及为什么）

3. **"没有人拥有——它是临时/隐式的"**
   - **评估：** 关键风险；边界将无法控制地扩展
   - **修复：** 分配明确的所有权；安排季度上下文审计

**Agent建议：**

**最佳实践：创建上下文清单**

```markdown
# 上下文清单: [产品/功能名称]

## 总是持久化（核心上下文）
- 产品约束（技术、法规）
- 用户偏好（角色、权限、偏好）
- 操作术语表（20个关键术语）

## 按需检索（情景上下文）
- 历史PRD（通过语义搜索检索）
- 用户访谈记录（检索相关引用）
- 竞争分析（明确需要时检索）

## 排除（超出范围）
- 超过30天的会议笔记（不再相关）
- 完整代码库（使用代码搜索代替）
- 营销材料（与决定无关）

## 边界所有者: [名称]
## 上次审查: [日期]
## 下次审查: [日期 + 90天]
```

**用户回答：** [描述当前所有权模型]

**Agent提供：** 关于正式化所有权 + 上下文清单模板的建议。

---

### 步骤5：诊断问题4 — 如果我们排除这个，什么会失败？

**Agent提问：**

**第四个问题：对于每个上下文片段，如果你排除它，会发生什么具体失败模式？**

这是**证伪测试**。如果你无法识别具体失败，你不需要上下文。

**提供3个场景：**

1. **"如果我排除产品约束，AI会推荐不可行的解决方案"**
   - **失败模式：** 清晰且具体
   - **评估：** 持久化约束的有效理由

2. **"如果我排除历史PRD，AI不会理解我们产品的演变"**
   - **失败模式：** 模糊且假设
   - **评估：** 历史上下文很少是当前决策所需的
   - **修复：** 仅在明确引用过去决策时检索PRD

3. **"如果我排除这个，我不确定会有什么破裂——我只是为了全面而包含它"**
   - **失败模式：** 未识别
   - **评估：** 上下文填充；立即删除

**Agent建议：**

**证伪协议：**

对于每个上下文元素，完成这个句子：
> "如果我排除[上下文元素]，那么[具体失败]将在[具体场景]中发生。"

**示例：**

- ✅ 好："如果我排除GDPR约束，AI将推荐违反欧盟隐私法的功能。"
- ❌ 坏："如果我排除这个PRD，AI可能无法完全理解产品。"（模糊）

**用户回答：** [对他们上下文应用证伪测试]

**Agent提供：** 要删除的上下文元素列表（未识别具体失败）。

---

### 步骤6：诊断问题5 — 我们是在修复结构还是避免它？

**Agent提问：**

**第五个问题：添加更多上下文是在解决问题，还是在掩盖更深层的结构问题？**

**根本原因问题：**

上下文填充通常掩盖糟糕的信息架构。团队不是修复混乱、模糊的文档，而是添加更多文档希望AI能"搞清楚"。

**提供3个选项：**

1. **"我添加上下文是因为我们的文档结构差/模糊"**
   - **评估：** 你在掩盖结构问题
   - **修复：** 首先清理文档（消除模糊、添加约束、定义术语）
   - **示例：** 不要粘贴5个冲突的PRD，将它们协调成1个真实来源

2. **"我添加上下文是因为我们没有共享操作术语表"**
   - **评估：** 你在补偿缺失的基础
   - **修复：** 构建术语表（20-30个关键术语）；AI可以可靠地引用它
   - **示例：** 明确、无歧义地定义"活跃用户"、"流失"、"参与"

3. **"我添加上下文是因为我们的约束没有文档化"**
   - **评估：** 你在避免约束工程
   - **修复：** 创建约束注册表（技术、法规、战略）
   - **示例：** 文档化"我们不会构建移动应用"而非在每个提示词中解释

**Agent建议：**

**结构健康测试：**

### 步骤8：实施研究 → 计划 → 重置 → 实施循环

**Agent提问：**

现在让我们实施**研究 → 计划 → 重置 → 实施**循环以防止上下文腐烂。

**问题：** 随着Agent研究，上下文中变得混乱——充满死胡同、错误和噪音。这稀释了注意力并导致目标漂移。

**解决方案：** 将研究压缩成高密度计划，然后在实施之前**清除上下文窗口**。

**四阶段循环：**

**阶段1：研究（允许混乱上下文）**

- Agent从多个来源收集数据
- 上下文窗口变得大而乱（这是预期的）
- 死胡同、失败假设和噪音积累
- **目标：** 全面的信息收集

**阶段2：计划（综合）**

- Agent将研究综合成高密度SPEC.md或PLAN.md
- 这成为实施的**真实来源**
- **关键元素：**
  - 做出的决定
  - 支持决定的证据
  - 应用的约束
  - 下一步（排序）
- **格式：** 结构化、简洁、明确

**阶段3：重置（清除上下文窗口）**

- **关键步骤：** 清除整个上下文窗口
- 删除所有研究工件、死胡同、错误
- 这防止上下文腐烂毒害实施

**阶段4：实施（仅使用计划的新鲜会话）**

- 使用**仅高密度计划**作为上下文开始新会话
- Agent有干净的、专注的执行注意力
- 没有研究阶段的噪音

**Agent提供3个选项：**

1. **"我想要PLAN.md格式的模板"**
   - Agent提供高密度计划的结构化模板

2. **"我想看这个循环的实际示例"**
   - Agent逐步讲解具体的PM用例（例如，发现规划）

3. **"我准备在我的工作流中实施这个"**
   - Agent提供逐步实施指南

**用户回答：** [选择]

**Agent提供：** 基于选择的定制指导。

## 示例

### 示例1：独立PM从上下文填充 → 工程

**背景：**

- 早期创业公司的独立PM
- 使用Claude Projects编写PRD
- 每次粘贴整个PRD（20页）+ 所有用户访谈（50份记录）
- 得到模糊、不一致的响应

**评估：**

- 症状：含糊响应、正常化重试（4+个症状）
- Q1（决定）："我只是想让AI理解我的产品"（没有具体决定）
- Q2（持久化/检索）：持久化一切（没有检索策略）
- Q3（所有权）：没有正式所有者（独立PM，临时）
- Q4（失败）：无法为大多数上下文识别具体失败
- Q5（结构）：避免约束文档化

**诊断：** 活跃的上下文囤积症

**干预：**

1. **立即：** 删除所有未通过Q4测试的上下文 → 保留原始的20%
2. **第1周：** 构建约束注册表（10个技术约束、5个战略）
3. **第2周：** 创建操作术语表（25个术语）
4. **第3周：** 为下一个PRD实施研究→计划→重置→实施

**结果：** Token使用量下降70%，输出质量显著提升，响应变得清晰且可操作。

### 示例2：拥有Agent链的增长阶段团队

**背景：**

- 5个PM的产品团队
- 用于发现综合的自定义AI Agent
- Agent A（研究）→ Agent B（综合）→ Agent C（建议）
- 每个Agent将完整上下文传递给下一个 → 上下文窗口爆炸到100k+ token

**评估：**

- 症状：不断上升的token成本、不一致的输出（3个症状）
- Q1（决定）：每个Agent有明确决定，但传递不必要上下文
- Q2（持久化/检索）：混合持久化和情景式但没有策略
- Q3（所有权）：没有明确所有者；每个PM添加上下文
- Q4（失败）：Agent"以防万一"传递上下文但没有可证伪失败
- Q5（结构）：缺少上下文清单

**诊断：** 无边界的Agent编排

**干预：**

1. **立即：** 定义每个Agent的有界上下文（Agent A仅向Agent B输出2页综合，而非完整研究）
2. **第1周：** 分配上下文边界所有者（Lead PM）
3. **第2周：** 创建上下文清单（什么持久化、什么检索、什么排除）
4. **第3周：** 在Agent B和Agent C之间实施研究→计划→重置→实施

**结果：** Token使用量下降60%，Agent链可靠性提升，成本降低50%。

### 示例3：拥有RAG但没有上下文工程的企业

**背景：**

- 拥有向量数据库RAG系统的大型企业
- "填充整个知识库"方法（10,000+文档）
- 检索每个查询返回50+块 → 淹没上下文窗口
- 随着知识库增长准确性下降

**评估：**

- 症状：尽管"完整知识"但响应模糊、正常化重试（2个症状）
- Q1（决定）：决定明确，但检索没有意图（返回一切）
- Q2（持久化/检索）：有检索的好直觉，但没有过滤
- Q3（所有权）：工程拥有RAG，产品不拥有上下文边界
- Q4（失败）：无法识别为什么需要50块 vs. 5块
- Q5（结构）：知识库没有结构（平面文档，没有元数据）

**诊断：** 无意图的检索（RAG作为上下文填充）

**干预：**

1. **立即：** 将每个查询的检索限制为前5块（从50下降）
2. **第1周：** 实施上下文检索（Anthropic）— 在索引期间为每个块添加解释性上下文
3. **第2周：** 为文档添加元数据（类别、新近度、权威性）
4. **第3周：** 产品团队定义每个查询类型的检索意图（发现 = 客户洞察，可行性 = 技术约束）

**结果：** 准确性提升35%（来自Anthropic基准），延迟下降60%，token使用量下降80%。

## 常见陷阱

### 1. **"无限上下文"营销 vs. 工程现实**

**失败模式：** 相信"100万token上下文窗口"意味着你应该使用全部。

**后果：** 推理噪音降低性能；准确率在约32k token后降至20%以下。

**修复：** 上下文窗口不是免费的。将token视为稀缺资源；优化密度而非容量。

---

### 2. **重试而非重组**

**失败模式：** "运行3次就能工作" → 正常化重试而不是修复结构。

**后果：** 浪费时间和金钱；掩盖更深的上下文腐烂问题。

**修复：** 如果重试常见，你的上下文结构坏了。应用Q5（修复结构，不要添加容量）。

---

### 3. **没有上下文边界所有者**

**失败模式：** 临时的、隐式的上下文决策 → 无限增长。

**后果：** 六个月后，每个查询在每次交互中填充100k token。

**修复：** 分配明确所有权；创建上下文清单；安排季度审计。

---

### 4. **混合总是需要与情景式**

**失败模式：** 持久化应该按需检索的历史数据。

**后果：** 上下文窗口被不相关信息充斥；注意力被稀释。

**修复：** 应用Q2测试：只持久化在80%+交互中需要的内容；检索其余。

---

### 5. **跳过重置阶段**

**失败模式：** 在研究→计划→实施循环中从不清除上下文窗口。

**后果：** 上下文腐烂积累；目标漂移；死胡同毒害实施。

**修复：** 计划后强制重置阶段；仅使用高密度计划作为上下文开始实施。
